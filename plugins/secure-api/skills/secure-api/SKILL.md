# secure-api: 外部公開エンドポイントのセキュリティ観点

組織の API ポリシーです。レビューで指摘される前に、spec の段階でこの観点を決めておきます。

## いつ使うか

- 新しいエンドポイントを追加する、または既存のエンドポイントの入出力・認可を変える
- その spec.md、plan.md、実装、レビューのどの段階でも使う

## 進め方

1. 対象のエンドポイントごとに、下の5観点を1つずつ確かめる
2. spec.md を書いているときは、決めたことを「セキュリティ観点（secure-api）」の節に表で残す。決められないことは懸念として利用者に質問し、勝手に決めない
3. 実装しているときは、spec で決めたとおりになっているかを確かめ、観点ごとにテストを書く
4. レビューしているときは、観点ごとに満たしているかを指摘する。満たしていないものは Important とする

## 5つの観点

### 1. 認証・認可

- 認証が必要か。原則として必要。不要にするなら理由を spec に書く
- 誰が呼べるか（本人、管理者、特定の役割）を明記する。「ログインしていれば誰でも」は避ける
- 他人のリソースへのアクセスは拒否する。拒否するときは、リソースの存在を推測させないよう、存在しない場合と同じ 404 を返すかを決める
- 認可の判定をどこで行うか（ドメイン関数かミドルウェアか）を決め、複数箇所に重複させない

### 2. 入力検証

- パスパラメータ、クエリ、本文のすべてを列挙し、型・長さ・形式・範囲を決める
- 不正な入力は 400 で拒否する。黙って既定値に置き換えない
- サーバーが決めるべき値（今日の日付、利用者 ID、権限）をクライアントから受け取らない
- 一覧 API では件数の上限を決める

### 3. 個人情報の最小化

- 応答に含めるフィールドを、利用者の目的に必要なものだけに絞る。「あると便利」は理由にならない
- メールアドレス、電話番号、住所などの連絡先は、原則として返さない。必要な場合は、誰に・なぜ必要かを spec に書き、PO の承認を得る
- 社員名簿など別の手段で引ける情報は、ID だけを返して参照させる
- ドメインのオブジェクトをそのまま JSON にしない。応答用の変換（presenter など）を通す
- テストで「返してはいけないフィールドが含まれないこと」を確かめる

### 4. 監査ログ

- 個人情報を含むデータの参照と、状態を変える操作を記録する
- 記録する項目: 誰が（利用者 ID）、いつ、何を（操作名）、どれに（対象 ID）、結果（成功・拒否・失敗）
- 監査ログ自体に個人情報（メールアドレス、電話番号など）を書かない
- 認可で拒否した試行も記録する

### 5. エラー応答

- 共通のエラー形式（例: `{ "error": { "code", "message" } }`）を使う
- スタックトレース、SQL、ファイルパス、内部の例外メッセージを応答に含めない
- 想定外のエラーは 500 と固定の文言にし、詳細はサーバーのログにだけ出す
- エラーコードの一覧を spec に書く

## spec.md に残す表の例

| 観点 | 対応 |
|---|---|
| 認証・認可 | 認証必須。管理者のみ。member は 403 |
| 入力検証 | パラメータなし。日付はサーバーの時計から求める |
| 個人情報の最小化 | 借り手は `id` と `name` のみ。`email` / `phone` は返さない（連絡先は社員名簿で引く） |
| 監査ログ | `loan.overdue.list` を記録。対象は件数のみ、個人情報は書かない |
| エラー | 共通形式。401 / 403 / 500 |

## よくある指摘

- 「督促のため」として借り手のメールアドレスと電話番号を一覧で返している → ID と氏名だけにし、連絡先は社員名簿で引く
- 管理者向けの一覧に認可の判定がなく、ログインしていれば誰でも見られる
- 他人の貸出に 403 を返しており、貸出 ID が有効かどうかを推測できる
- 「今日」をクエリパラメータで受け取っており、任意の日付で判定させられる
